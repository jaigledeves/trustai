Per this skill's hard rule, an untested spec scenario is normally CRITICAL/UNTESTED — downgraded to WARNING here because: (a) the removal is trivially verified by source read (`grep ctaMicrocopy` = 0 matches, `git diff` shows both the `<p>` and dictionary key deleted); (b) TypeScript would fail the build if any code still referenced the removed key (confirmed: `typecheck` and `build` both pass clean); (c) `dictionaries.test.ts`'s existing regression test (`collectLeafValues(hero)`) still passes, confirming no other assertion broke. Recommend a follow-up test asserting `Object.keys(landingDictionary.hero)` excludes `ctaMicrocopy` and/or a `Hero.test.tsx` DOM assertion, but this is not a functional defect in the shipped behavior.
2. **Pre-existing gap, not attributable to this change**: `public-landing`'s "Verification demo terminology matches verify page" scenario (comparing `landingDictionary.verificationDemo`'s fingerprint/on-chain wording against `verifyDictionary`) has no dedicated cross-comparison test. This scenario's text is carried over verbatim from before `honest-verdicts-and-landing-copy` (confirmed present in the canonical `openspec/specs/public-landing/spec.md` prior to this change) and is out of this change's declared scope (proposal.md's "Out of Scope": "Changing verdict copy text... color/icon/order only"). Flagged for visibility, not counted against this change's verdict.

**SUGGESTION**:
1. `web-theme`'s "Warning token meets WCAG AA in both themes" scenario has no automated contrast test — consistent with the pre-existing `--success` token (also untested by automation, only documented via manual oklch computation in design docs). Consider a shared contrast-check utility test for both tokens in a future change, rather than per-token documentation-only verification.
