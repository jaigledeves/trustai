## Exploration: rebuild-public-landing

### Current State

`apps/web/app/page.tsx` is a Server Component (no client JS) rendering the public marketing landing at route `/`. It already follows RNF-041 (all copy from `dictionaries/es/landing.ts`), uses `Wordmark`, `Button` (shadcn/radix), and reads `config.chainExplorerBaseUrl` / `config.demoDtrId` for the contract-explorer link and the optional demo-verification CTA. Sections today: header (nav), hero, "how it works" (4 steps, static, non-interactive), trust pillars (3 items), final CTA, footer. There is **no dedicated test** for `page.tsx` (`Glob` found none), unlike other page-level Server Components in this app (`app/verify/[id]/page.test.tsx`, `app/(dashboard)/dtrs/[id]/page.test.tsx`, `app/(auth)/verify-email/page.test.tsx` all exist) — a coverage gap relative to project convention, not just to this change.

The approved v0 mock at `mockups/landing/trust-ai-landing-page/` is a throwaway Next.js reference app with 9 sections/components (`site-header`, `hero`, `how-it-works`, `verification-demo` — the only client-interactive one (`'use client'`, local `tampered` toggle) —, `use-cases`, `pillars`, `faq`, `final-cta`, `site-footer`) plus its own `logo.tsx`, `ui/button.tsx` (`@base-ui/react` wrapper), and `app/globals.css`. All copy is hardcoded JSX literals (expected — it's a mock) and several factual claims are inaccurate relative to the real backend (see Risks).

### Affected Areas

- `apps/web/app/page.tsx` — full rebuild: keeps Server Component shell, composes new section components, adds a client-island wrapper for the interactive verification demo.
- `apps/web/dictionaries/es/landing.ts` — extended with new keys for use-cases, FAQ, and the reworded hero/how-it-works/pillars/CTA copy (RNF-041, no inline JSX literals).
- `apps/web/dictionaries/es/dictionaries.test.ts` — currently does **not** include `landingDictionary` in its `it.each` non-empty-string guard; must be extended, and likely needs a dedicated `describe`/`it` block for the accuracy-sensitive copy (mirrors the existing `authDictionary`/`certifyDictionary` exact-copy assertions).
- `apps/web/app/globals.css` — open question on `--success` / `--success-foreground` / `--success-muted` tokens (see Open Questions); light-mode block only, no `.dark` or `@media (prefers-color-scheme: dark)` addition.
- New directory `apps/web/components/landing/` (suggested, does not exist yet) — target location for ported section components (hero, how-it-works, verification-demo client island, use-cases, pillars, faq, final-cta) plus supporting tests.
- `apps/web/components/brand/Wordmark.tsx` — already the real app's header/footer glyph; the mock's `logo.tsx`/`LogoMark`/`Wordmark` duplicate is NOT ported, `Wordmark` is reused as-is (iconOnly prop already supports the footer use).
- `apps/web/components/ui/button.tsx` — real shadcn/radix `Button` is reused for CTA buttons; the mock's raw `<a>`/`<button>` markup and its `@base-ui/react`-based `ui/button.tsx` are NOT ported.
- `apps/web/lib/config.ts` — `config.chainExplorerBaseUrl` and `config.demoDtrId` remain the source of truth for the contract-explorer link and the optional "see a live example" CTA (`demoDtrId` is `undefined`-able; current page already guards it with `config.demoDtrId ? ... : null`, same pattern must carry over).
- `apps/web/dictionaries/es/verify.ts` + `apps/web/components/verify/ClientHashRecompute.tsx` — read-only reference for the honest verification-demo copy; the four verdict labels/messages (`VALID`, `ASSET_MISMATCH`, `PENDING_ANCHOR`, `INVALID_RECORD`) and the hash-recompute caveat must be echoed accurately, not re-authored inconsistently, in the new landing demo section.

### Requirements & Constraints (concrete)

1. **RNF-041 dictionary keys.** Every string in every ported section must resolve through `landingDictionary`. Concretely, `landing.ts` needs new top-level groups beyond today's `nav`/`hero`/`how`/`pillars`/`cta`/`footer`:
   - `useCases: { title, subtitle, items: [{ title, description }] }` (6 items in the mock — content-audit rework required, see #6 below).
   - `faq: { title, subtitle, items: [{ question, answer }] }` (6 Q&As in the mock — pricing/future-plans item must be dropped or rewritten per #6).
   - `verificationDemo: { badge, title, description, toggleOriginalLabel, toggleTamperedLabel, ... }` plus reuse (not re-author) of `verifyDictionary.verdicts` and `verifyDictionary.recompute` for the actual verdict copy shown.
   - `dictionaries.test.ts` must import and register `landingDictionary` in its `it.each` list (currently misses it — pre-existing gap, not caused by this change, but must be closed as part of it).
2. **Light-mode only.** Do not port `mockups/.../app/globals.css`'s `.dark` class block or its `@media (prefers-color-scheme: dark)` block. No `next-themes`, no dark toggle anywhere in the ported markup (mock's `dark:` Tailwind variants in `ui/button.tsx`, which isn't ported anyway, are moot).
3. **Terminology.** "Registro Digital de Confianza (DTR)" is the one term for the central artifact across all new sections — the mock is inconsistent (`hero.tsx` line 74 uses this exact phrase; `landing.ts`/`how.ts` current copy uses "Digital Trust Record" in English — that must be unified to the Spanish expansion + DTR acronym everywhere in the rebuilt copy).
4. **Honest verification demo.** The ported `verification-demo.tsx` (mock) claims the *recipient's browser* recomputes "the file's hash" and compares it against "the hash on blockchain" — this is false for two reasons: (a) `ClientHashRecompute.tsx`'s own docstring states public DTOs never expose `canonicalHash`/asset hash, so no client-side comparison against an on-chain value is possible; (b) what's anchored is not "the file's hash" but the SHA-256 of the DTR's RFC 8785 canonical serialization (`packages/dtr-core`), a different value from the raw file hash. The rebuilt demo must instead show the 4 real backend verdicts (`VALID`/`ASSET_MISMATCH`/`PENDING_ANCHOR`/`INVALID_RECORD`, from `verify.ts`) — most plausibly as a client-island toggle that swaps between pre-baked example states of each verdict's title/message (sourced from `verifyDictionary.verdicts`, not re-authored) — and may state the browser independently recomputes the file's SHA-256, carrying the exact same caveat text pattern as `verifyDictionary.recompute.caveat`.
5. **Anchoring copy accuracy.** Any "what gets anchored" claim (hero card, how-it-works step 3/4, FAQ) must say "the SHA-256 hash of the DTR's canonical (RFC 8785) serialization is anchored on-chain", not "the file's hash is anchored". The current `landing.ts` (`how.steps[2].description`) already gets this right ("El Digital Trust Record se serializa de forma canónica y se calcula su hash SHA-256"); the mock's hero card and how-it-works copy get it wrong ("its own digital fingerprint", implying file-hash-only) and must be corrected on port, not copied verbatim.
6. **Content-audit corrections to apply while porting** (already agreed, not open):
   - Use-cases: rewrite mock's 6 items to integrity+timestamp claims only — remove/soften "Contratos" ("exactamente la que se acordó" implies authorship/legitimacy), "Títulos y certificados" (implies issuer legitimacy, not just integrity), "Obra creativa..." ("era tuyo" is an ownership claim TrustAI cannot back). Each item should read as "this file existed, unmodified, since timestamp X" — not "this fact about the world is true" or "this party is who they claim".
   - FAQ: mock's "¿Tiene costo?" answer promises "Los planes para mayor volumen se anunciarán más adelante" — a future-plans/pricing promise; remove this FAQ item or rewrite without any pricing/roadmap commitment.
   - How-it-works step 1: mock says "Se procesa de forma segura" (vague); must say "cifrado (AES-256-GCM)" per the locked correction (matches whatever storage-encryption fact is true in the certify pipeline — verify against `apps/api` before finalizing wording in spec phase).
7. **Config-driven hrefs** (must NOT hardcode): `/login`, `/register`, `/verify/${config.demoDtrId}` (guarded — `demoDtrId` may be `undefined`, hide the CTA when unset, same pattern as today's `page.tsx` lines 60-66), and the contract-explorer URL built from `config.chainExplorerBaseUrl` + the `AnchorRegistry` address (currently a literal `ANCHOR_CONTRACT` constant in `page.tsx` — carries over unchanged, it's a public deployed-contract address, not a secret or an env-configurable value today).
8. **Dependencies.** `lucide-react@^0.468.0` already present — reuse mock's icon choices (`ArrowRight`, `Check`, `FileText`, `Upload`, `Sparkles`, `FileCheck`, `Boxes`, `Search`, `Fingerprint`, `BrainCircuit`, `FileSignature`, `GraduationCap`, `Receipt`, `Palette`, `Scale`, `ShieldCheck`, `X`) with no new dependency. Do NOT add `@base-ui/react`, `class-variance-authority` is already presumably present via existing `components/ui/button.tsx` (confirm shadcn's cva usage matches) — no new dep expected here either.

### Approaches

1. **Section-by-section port into `apps/web/components/landing/`, page stays a thin composition** — create one component per section (`Hero.tsx`, `HowItWorks.tsx`, `VerificationDemo.tsx` as `'use client'`, `UseCases.tsx`, `Pillars.tsx`, `Faq.tsx`, `FinalCta.tsx`), each importing only from `landingDictionary` (+ `verifyDictionary` for the demo section), `app/page.tsx` becomes an ordered composition of these plus the existing header/footer markup (kept inline or also extracted).
   - Pros: matches existing project granularity (`components/verify/*`, `components/certify/*` are one-file-per-concern with colocated `*.test.tsx`); each section independently testable; smallest possible client boundary (only `VerificationDemo` is `'use client'`).
   - Cons: more files to review than a single big `page.tsx`; needs the new `landing.ts` dictionary shape agreed before any component is written.
   - Effort: Medium.

2. **Keep everything inline in `app/page.tsx` (current pattern), just extend it** — grow `page.tsx` in place the way it is today (all sections inline JSX), only extracting the verification-demo interactive bit into its own client component (unavoidable — Server Component can't hold `useState`).
   - Pros: minimal new files, smallest diff to review for the page shell itself.
   - Cons: `page.tsx` would balloon past ~170 lines to likely 350+ once use-cases/FAQ are added, working against the existing `components/*` decomposition convention elsewhere in the app; harder to unit-test individual sections; conflicts with the review-workload guard (400-line budget) more directly by concentrating all diff in one file.
   - Effort: Low upfront, higher long-term maintenance cost.

### Recommendation

Approach 1 (dedicated `apps/web/components/landing/` directory, one component per section, `page.tsx` as thin composition). It matches the codebase's existing pattern (`components/verify/`, `components/certify/`, `components/history/` are all one-component-per-file with a colocated `*.test.tsx`), keeps the Server/Client boundary minimal and explicit (only the verification-demo island is `'use client'`), and produces reviewable, independently testable units that fit the 400-line PR budget more naturally than one large `page.tsx` diff.

### Open Questions

1. **`--success` / `--success-foreground` / `--success-muted` tokens.** The mock's `globals.css` defines these (light `oklch(0.62 0.15 155)` + dark variants) and its `hero.tsx`/`verification-demo.tsx` use `text-success`, `bg-success-muted`, `bg-success` directly. The real `apps/web/app/globals.css` has no such tokens at all — today's real landing signals "success"/"live" state with a raw `bg-emerald-500` dot (`page.tsx` line 47) instead. Two options for sdd-design to decide: (a) add the 3 tokens to `:root` only (light-mode-only, per constraint #2, so no `.dark` variant needed) as a small, scoped design-system extension; or (b) map every mock `success`/`success-muted` usage to existing Tailwind emerald utility classes (`text-emerald-600`, `bg-emerald-50`, etc.), avoiding a design-token change entirely. Recommend (b) for a smaller footprint unless other upcoming work also wants a semantic "success" token.
2. **Component location confirmation.** Recommending `apps/web/components/landing/` (new directory) — needs explicit sign-off in the proposal/design phase since it's a new top-level grouping alongside `verify/`, `certify/`, `history/`, `auth/`, `brand/`.
3. **Verification-demo test coverage.** Given `strict_tdd: true` and the existing precedent (`components/verify/ClientHashRecompute.test.tsx`, `HashOnlyCard.test.tsx`, `UploadVerdictPanel.test.tsx` all exist for the real verify flow), does the landing's interactive verdict-toggle demo need its own `VerificationDemo.test.tsx` covering: renders each of the 4 verdicts' copy correctly, toggle switches state, no crash when `demoDtrId` unset for the "see a real verification" link? Recommend yes — this is new interactive logic, not just markup, and strict_tdd applies.
4. **`dictionaries.test.ts` shape assertion.** Beyond adding `landingDictionary` to the generic non-empty-string `it.each` loop, should a dedicated `it()` assert the exact terminology string ("Registro Digital de Confianza (DTR)") appears verbatim somewhere in `landingDictionary` (mirroring the existing exact-copy tests for `authDictionary`/`certifyDictionary`)? Recommend yes, to lock terminology consistency the same way `errorInvalidCredentials` is locked today.
5. **Step 1 encryption claim ("cifrado (AES-256-GCM)").** Needs a one-line verification against the actual storage/encryption implementation in `apps/api` (not explored in this pass) before the exact algorithm name is committed to spec — flagging so sdd-propose/spec doesn't inherit an unverified technical claim.
6. **`app/page.test.tsx` — new or first-ever?** Since no test exists for the current `page.tsx` at all, should this change (a) just add the missing baseline test for the rebuilt page as part of this change, or (b) treat the missing test as pre-existing debt out of scope? Recommend (a): strict_tdd plus the fact every other page-level Server Component in the app already has one makes this the natural moment to close the gap, and it's needed anyway to assert config-driven hrefs / demoDtrId guard behavior on the new page.

### Risks

- **Accuracy regression if mock copy is ported verbatim.** The mock's hero card and verification-demo section make claims (file-hash-only anchoring, browser-side on-chain comparison) that are false for this system's actual DTO/anchoring model — already identified and covered by constraints #4/#5, but this remains the single highest-risk item: an unreviewed literal port would ship marketing copy the product cannot back up.
- **Terminology drift.** Existing `landing.ts` uses "Digital Trust Record" (English) while the locked decision is the Spanish "Registro Digital de Confianza (DTR)" — every string that references the artifact needs conscious rewriting, not just addition of new sections; missing one instance re-introduces inconsistency the content audit was meant to fix.
- **Server/Client boundary creep.** Only the verification-demo section legitimately needs `'use client'`. Risk of over-porting the mock's client-side patterns (e.g. if FAQ's native `<details>`/`<summary>` — which needs no JS — gets reimplemented as a controlled React component unnecessarily) would silently grow the client bundle and contradicts the "page stays a Server Component overall" constraint.
- **Test coverage under `strict_tdd: true`.** New interactive logic (verification-demo toggle) and a page with zero pre-existing test coverage both need RED-GREEN-REFACTOR treatment; underestimating this in tasks-phase planning risks either skipped tests or task-list bloat that busts the review budget.
- **`demoDtrId` optionality.** `config.demoDtrue` (typo guard: it's `config.demoDtrId`) is `undefined` by default (no operator-set demo record) — every place the mock or new copy references a "try a real example" link must tolerate this being absent, exactly as today's `page.tsx` already does (`config.demoDtrId ? ... : null`). Missing this guard in a new section is an easy regression.
- **`--success` token scope creep.** If sdd-design chooses to add the `--success*` tokens, scope discipline is needed to keep it a small, additive, light-mode-only change and not an opportunity to also touch `.dark`/`@media` blocks (explicitly out of scope per the light-mode-only constraint).

### Ready for Proposal

Yes. The terrain is well-understood: current landing structure, mock content to port, design-system gap (`--success` tokens), honesty corrections needed on the verification demo and anchoring copy, and the dictionary/test conventions to follow are all concrete enough to write a proposal. Two items should be explicitly resolved during proposal/design rather than left implicit: the `--success` token decision (recommend mapping to emerald utilities, open in the proposal for confirmation) and the new `apps/web/components/landing/` directory location (recommend for sign-off, not re-litigation from scratch).
